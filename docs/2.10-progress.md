### Carry-overs from Stage 2
1. **chats.json data loss (both OSes).** If `chats.json` can't be read, Still moves it to `chats.json.broken-<time>` and says so once in the chat panel. Attachments are no longer deleted. If the file can't be moved, nothing is saved over it for the rest of that run. Tested by tests/desktop/chatsfile.py, which uses a corrupt file, an unreadable file and a locked file.
2. **Mac storage shared across profiles.** On macOS 14 and later each profile's interface gets its own `WKWebsiteDataStore(forIdentifier:)`, built from the profile id (`Profiles.shellStore`), and deleting the profile removes it. Below macOS 14 the default store is still shared. The drafts workaround in tabkeep.py has been removed.
3. **Mac exchange Undo, Copy and Paste.** The real cause was in the test path, not the app. The Mac QA bridge handed test key presses straight to the page view, skipping the app's event queue. Real key presses go through that queue, and AppKit closes an undo step between events, so the test's edits all merged into one undo step. Undo then emptied the box. The Copy check runs right after an undo and Paste uses what Copy gave, so both failed after it. QA key presses now go through the event queue like real ones (`qaPost` in `Qa.swift`), and exchange.py waits a little longer on the Mac for each queued key. In the app, removing a mention was already its own undo step once real key events were used. Result: exchange 77/77 on the Mac.
4. **welcome.py on the Mac** now closes the second QA app it starts.
5. **Flaky Windows tests.**
   - features.py now waits for the opener's line to be written before reading it.
   - library.py's "Pasting a shared companion" didn't fail in any run during Stage 3: about 12 runs, including a copy that timed the step. The cause wasn't found, and the test is unchanged. If it fails again, the timing copy is the place to start.
6. **Mac AI apps left by a crash.** Each run is now started in its own process group and listed in `running-ai.txt` under the profile, with its start time. At the next start Still ends any process from that list, but only if its start time still matches, so an unrelated process that reused the pid is never touched. This now covers every chat, not just incognito chats. Tested by tests/desktop/orphans.py, which kills Still mid-run.

### R9: tasks, states and resume
- **States.** Each run is a task in `ai/tasks/<chat>.json`, in one of these states: running, paused (Take over, or a site sign-in), waiting (with a reason: approval, answer or signin), interrupted, completed or failed. An incognito chat's task is kept in memory only. Windows code: `still/MainWindow.Tasks.cs`. Mac code: `mac/Sources/Still/Tasks.swift`.
- **Checkpoints.** After each tool step the task saves the step (what was done and whether it worked), the agent's own tabs (never private tabs), what it's waiting on and the last audit entry.
- **Sensitive steps.** The intent is written to disk before the step runs. When it finishes, the outcome is written: done or failed. A step cut off in between keeps no outcome, so it counts as uncertain.
- **After a restart.**
  - Running, paused and waiting tasks become interrupted, because no AI app runs before Still does.
  - Approvals given in a chat are cleared. Rules in Settings stay.
  - One offer per launch lists the interrupted chats by name.
- **Resume.**
  - Resume all (in the offer: "Resume the others") skips any task with an uncertain step. That task is resumed from its own chat.
  - Before an uncertain step can run again, the companion is told to check the site first. The next sensitive step always asks with a card, even if a rule would normally allow it with the 8-second countdown.
- **Resume brief.** A resumed run is told:
  - what it was asked
  - its steps
  - its tabs
  - what it was waiting on
  - which steps may not have gone through
  - to read each page again
  - to start its reply with what was already done and what it checked again
  The chat also gets a note: "Picked up where it stopped after N steps".
- **Lost session.** If the AI app can't restore the session ("No conversation found"), or a session was never saved, Still starts a new session from the checkpoint and says so in the chat. A session is now saved as soon as the AI app names it, not at the end of the run.
- **Signed out or missing AI app.** The task waits with Sign in and Resume buttons in the chat.
- **Quitting.** Quitting Still mid-task leaves the task unfinished, so the next start offers it.
- **Kept working:** parallel runs and the follow-up queue, Stop (now completed with the reason "stopped"), Take over, session resume and lost-session replay, the 1-hour cap.

### R24: message box drafts
- Each chat's box and the new tab page's box keep the text, the mentions and the attached files. They come back after switching views, closing the tab or chat, and restarting Still.
- Sending clears the draft. Restored text is shown with the cursor at the end.
- Saving happens 300 ms after the last change, and right away on leaving the box or Still.
- A new chat's draft moves to the chat's id once it has one.
- Drafts older than 7 days are dropped when Still starts.
- Attached files that haven't been sent are kept for 7 days (`ai/attachments`). A file that's gone is quietly dropped when the draft comes back (`aiReattach`).
- Incognito: drafts are kept in memory only. On Windows the interface storage is shared between regular and incognito windows until Stage 5, so this check matters. Drafts are never written to `chats.json`.

### Defaults used
- After a restart, one offer per launch lists the interrupted tasks. A task with a pending sensitive step is never resumed automatically (batch default).
- Unsent drafts older than 7 days are dropped (batch default).
- Attachments not sent are kept 7 days, the same as drafts.

### Decisions made
- The main window's new tab draft survives a restart. Other windows' drafts last while the window is open, because windows don't keep ids across restarts.
- Approvals given in a chat are cleared at every start.
- The user's Stop is recorded as completed with the reason "stopped", not failed.
- "Not now" hides the offer for this launch. Each interrupted chat still shows its own Resume bar.
- For AI apps added by manifest, the lost-session restart is turned on when they resume a session. Before, only Claude and Grok had it.
- Step records are what Still saw (the tool calls), not the AI app's own plan. Still has no access to that plan.

## Stage 4: Delegation as sub-agents

Branch `still-2.10/stage-04-sub-agents`, from `still-2.10/stage-03-tasks-resume` (6bcc0fe).

### R11: companions help each other as child tasks
- **Child tasks.** When a companion asks a teammate (ask_companion) or hands work over (tell_companion), the teammate works on a child task of the asking chat. It gets only what it was asked, with its own role, skills and tools. A child of an incognito or off-the-record chat is the same. Both tools take an optional `title`, a few words for what's asked ("a pitch"). The child chat is titled from it ("Maya asked Jonah for a pitch").
- **Results come back.** An ask waits for the result. A tell runs in the background, and its result lands on the card in the asking chat when it's done. The helper is told to name its sources (links) and what it couldn't find or isn't sure of. The asker gets the result with a note to keep those sources in its answer.
- **Failure and cancel.** A child that fails or is stopped puts "Still missing: <what was asked for>." on its card. The asker gets that too, so its answer says what's missing.
- **Memory.** A child task can recall, but remember, forget and update_knowledge are refused with "You're helping Maya, who decides what's kept: put what's worth remembering in your reply." A child's chat isn't saved to memory as a past chat.
- **Permissions.** A child acts only where everyone up the chain may. For each site and action, the strictest rule wins: Ask over Allow in this chat over Always, and anything unknown asks (`still/Agents/Delegation.cs`, Mac `strictest` in `Ai.swift`). Approvals a child needs show in the user's chat, the root of the request, on the card naming the companion who asks. "Allow in this chat" there counts for the whole request.
- **History.** Child tasks aren't in Chat History, the side list or the New replies menu. Their cards open them. Deleting a chat deletes its child tasks.
- **Kept working.** 3 hops deep, about 10 messages per request, no loops, none messages itself, Stop cascades to children, and each companion's role and skills.

### R12: where companions browse
- **The setting.** Settings → Privacy & permissions → Where companions browse → "New chats browse in":
  - Your profile (the default, and what every existing user keeps): companions are signed in wherever the user is, as before.
  - Companion profile: a separate profile with its own sign-ins and cookies. Companions only get the sites the user signs in to there.
- **Separate engines.** Windows: a second WebView2 profile, "Companion", in the same environment. Mac: `WKWebsiteDataStore(forIdentifier:)` with its own id per Still profile on macOS 14+. Nothing is copied into it: no cookie, password or session.
- **Per chat.** A chat keeps the profile it started with (`AiChat.Profile`; older chats have none and stay in the user's profile). Under the message box a chip shows "Your profile" or "Companion profile". Picking the other one closes the chat's pages, adds a note to the chat ("Now browsing in the companion profile: its own sign-ins, apart from yours.") and tells its AI before its next step: "[Still] The user switched this chat to browse in the companion profile: … Your earlier pages were closed. Before you act on a site, check who you're signed in as." The chip is disabled while the chat works. Child tasks keep their parent's profile.
- **Everything it opens stays in it.** Its tabs, links and pop-ups from its pages, web_search and read_url (a third hidden lookup page on Windows, the companion store on the Mac). The site info cookie list shows the profile of the tab in view.

It signs companions out of every site in their profile and leaves the user's sign-ins (Windows `ClearBrowsingDataAsync(AllProfile)` on the Companion profile, Mac `removeData` on the companion store). ### R16: skills load only when the companion asks

Any id the companion doesn't have is refused with "You don't have a skill with the id ...", so a teammate's skill or a made-up id never loads, and nothing matches by keyword. Each load adds one "Used skill X" step; index-only turns add none. The step icon pattern covers "Used skill" and the older "Loaded skill" rows.
- **Typed /id.** A skill the user names with `/id` still goes into that turn, and shows as "Used skill X" too.
- **Helpers.** A teammate asked for help runs through the same `RunAi`, so it also starts with its own index only.

### R15: next steps and chat spacing
- **Next steps** moved to `nextSteps.ts`. Only the trailing run of suggestion lines outside code fences counts. A "Next steps" label line just before them goes too. Lines past the limits show as plain text without the marker, never as raw `>>`.
- **One prompt sentence on both OSes**: "When it helps, end with up to 3 next steps the user can pick. They are the last lines of your reply, each exactly ">> " and plain text, with no bold, bullets or numbers and nothing after them." The "short bold line" wording is gone (batch default).

### R7: images and videos in replies

### R6: runtime quality
- **Memory.** A chat's first turn gets only facts that share a word with the message or are core: name and other keyed facts, preferences, people, and everything the user wrote in setup or on the memory page. Past chats come only when related. `remember` takes `guessed` for a fact worked out from what the user did: the prompt lists those apart under "Guessed from what they did, not confirmed (check before relying on them):", the memory page marks them Guessed, not confirmed, and an edit by the user confirms one.
- **Instructions.** One generic line went (pages showing beside the chat). "Keep going" became five standards: keep going without asking for harmless steps; check your work and never claim a step you didn't take, and say when you only linked media; a one-line update before each big step; after a failure try another way, and when the same thing fails twice stop and say what blocked you; finish with the result first, then assumptions and what's open.

- **Settings → Models → API providers** (`ApiProviders.tsx`): kind (OpenAI-compatible Chat Completions or Anthropic-compatible Messages), name, base URL, key, models (loaded from `GET /models` where offered, else typed), prices per million tokens in and out, a monthly limit and a context size. - **Cost.** Each reply's tokens and estimated cost, and the chat's running total, under the chat ("Last reply: 6.9k in, 61 out, about $0.0215 · This chat: ..."). A monthly total per provider in Settings, split by chats, chat titles, setup and tests. An optional monthly limit pauses the provider's runs: "paused: this month's spending reached your limit of $5. ## Stage 9: Companion memory and first-use setup

Branch `still-2.10/stage-09-memory`, from `still-2.10/stage-08-instructions` (18521dd).

### Memory items with sources and versions
- Each memory keeps its chat and the message it came from, its source (chat, inferred, settings, onboarding, legacy), who it's about (`Subject`), when it was made and last changed, and when it was last used (`still/CompanionMemory.cs`, `mac/Sources/Still/Memory.swift`).
- A newer version supersedes the old one (by `replaces` or the same slot): the old stays as history with `Status: superseded`, never goes into a prompt or recall, and the memory page lists it under Earlier versions. A correction replaces the closest item about the same person (word overlap 0.4 or more).
- The same thing said again freshens the old item instead of adding a copy, but only when the words mostly match (0.75) and the numbers, names, subject and yes-or-no all match: "Drinks coffee at work" and "Drinks no coffee at work" stay two items.
- One memory is 300 characters at most; the refusal says the chat keeps the details and open_memory_source finds them.
- Files from before 2.10 migrate on first read: each item gets a source (Settings when it has no chat, otherwise chat or inferred), and the old one-line past chats become summaries marked "from before 2.10, not checked".

### Recall, retrieval and the brief
- BM25 over active memories and chat summaries, light stemming, a fixed alias list and a floor (0.3), so an unrelated question brings nothing. The corpus counts as at least 10 items, so with one or two memories a matching word still clears the floor.
- The first turn of a session gets profile items (own 400-character budget) and then what fits the message, the last four messages and this chat's own summary, about 1,500 characters in all, at most three past chats. Guessed items are listed apart as not confirmed.
- Later turns get no memory block: they get the change note instead.
- recall returns memories with id, date, source, guessed and how many earlier versions, and past chats with "checked against the chat" or not; with nothing found it says not to guess. open_memory_source returns the messages a memory or a summary came from.

### Forget, tombstones and the secret filter
- forget by id takes every version; by words, every active item holding all of them, and more than three matches forgets nothing and returns the list to check. An empty forget is refused on both platforms.
- What's forgotten leaves a tombstone: a hash of the item and a hash of each word, never its text (`forgotten.json`). remember refuses a near match ("The user asked you to forget that"), and summary lines that hold all its words are dropped, unless the user says it again in their own message (60% of its words in their last message), which lifts the tombstone.
- The secret filter works by shape: PEM keys, JWTs, known key prefixes, a value after "password is", "PIN:" and the like, card numbers that pass Luhn, IBANs that pass mod-97, and random-looking tokens (letters and digits, entropy 3.5 or more). Ordinary mentions pass ("API keys", "my password is saved in 1Password", "card numbers are on the back").

### Files that survive a crash
- Every memory, summary and knowledge write goes to a temp file, flushed, then replaces the old one, which stays as .bak.
- A file that can't be parsed is kept as `<name>.corrupt-<time>.json`, the .bak loads, and a toast says so once. If it can't even be moved, Still never saves over it that run.
- A write that fails rolls back: remember returns "Still couldn't save that to memory... Nothing was remembered", and the chat step reads "Didn't save to memory" (the Stage 8 live run had found "Saved to memory" on a refused write).

### Chat summaries
- A chat quiet for 10 minutes, with two or more user messages, gets one summary on its AI's efficient model, with no tools: goal, constraints, decisions, corrections, done, open and next step, each line under 200 characters and linked to real message numbers.
- A run that didn't finish (failed, stopped or interrupted) has no done lines: they become "Not finished: ...".
- Never incognito, off-the-record, delegated or routine chats, chats from before 2.10, or a chat forgotten since (unless it changed after). Each line goes through the secret filter, the form-data and private-tab checks and the tombstones.
- Settings has a Summarize chats switch; each companion's memory lists its summaries with Forget this chat.

### Change notes
- Each change to a companion's memory, instructions or knowledge is noted (in memory only, the last 200). An open chat's next turn starts with "[Still] Since your last turn, outside this chat:" and the changes it hasn't heard, under 600 characters. A forgotten item is named by id only.

### Knowledge files
- The prompt lists each file (name, id, version, size, last update, what it holds), not its text. read_knowledge returns the text and version; update_knowledge needs that version and refuses a stale one with the current text. Each write keeps a revision (the last 10); the profile has Undo last change, and Reset knowledge puts back the role's empty seeds.
- Incognito chats read knowledge, never write it; the incognito prompt now says memory is read only there.

### Setup state and activation
- `Companion.Setup` is pending or done, with `SetupAt`, `SetupVersion` and `SetupChat`. `Greet: true` migrates to pending, false or missing to done.
- Setup loads in a companion's regular chats only (never incognito, delegated or routine) until it has answered the user once; a resumed session that already has it doesn't get it again.
- A hidden activation note says whether this is the first use or they've met before, how many things the user told Still (and how many in setup), crew or Make your own, and whether the user's message is the first task.
- The kickoff no longer saves the first question's answer to memory itself: the companion's Setup saves what's worth keeping.
- Introduce yourself again sets Setup pending; Clear personalization resets Role, Personality and Reply length and forgets what was learned in the Setup chat; Reset everything clears memory, summaries and knowledge, sets Setup pending and drops the sessions of that companion's idle chats.

## Stage 18: Drafts and undo

Branch `still-2.10/stage-18-drafts`, from `still-2.10/stage-17-companion` (223533f).

### 1. Drafts are kept by Still, not the page
- Before, the message boxes kept drafts in the interface's own storage. A check this stage showed a hard kill (`taskkill /T /F`) loses what was written there in the last moments, so drafts now go to Still: one file per box in the profile (`ai/drafts/<key>.json`; Windows `SaveDraft` and `LoadDrafts`, Mac `saveDraft` and `loadDrafts`). Still sends them to the interface when it loads, before the first state, so a box finds its draft when it shows.
- Saved half a second after the last change, and at once when the box loses focus or the page goes.
- Boxes that keep drafts: the New Tab box, every chat's box, the side chat's, the answer box on a companion's question, setup's answer box and a routine's What to do. Each chat and each companion's box has its own; the main window's New Tab has one. Another window's New Tab draft lasts while that window is open.
- Comes back after a refresh, closing the tab or chat, Still being killed, and a restart, with a small Draft restored hint and Discard. Discard empties the box and deletes the draft (Ctrl+Z brings it back).
- Drafts the interface kept itself before move into Still's files on the first start, then leave the page's storage.
- A private window keeps nothing on disk: the host ignores its drafts, and the interface keeps them in memory only. Password and key fields are never part of a draft or of undo.
- A draft not touched for 7 days goes.

### 2. Send clears it only once Still took the message
- The box sends its draft key with the message. Still answers `sent` (ok or not). Ok deletes the draft and its undo steps (unless more was typed meanwhile). Not ok keeps the draft and puts the text back in the box, with Still's reason as a toast.
- The one send Still turns down today is a message over 20,000 characters: "Messages can be up to 20,000 characters. Yours is still in the box." Both hosts used to drop it silently.

### 3. Save drafts toggle
- Settings → General → Save drafts, on by default. Turning it off asks first ("Turn off Save drafts?"), then, after the usual Undo, deletes every draft. With it off nothing is kept, and nothing comes back after a refresh or a restart. Turning it on needs no confirm.

### 4. Undo and redo in every Still text box
- Ctrl+Z and Ctrl+Shift+Z, and Ctrl+Y on Windows; Cmd on the Mac (Edit → Undo goes to the same steps). In the message boxes and every input and text area, never a password or key field.
- Step by step: typing runs together until a pause of a second or a new word. Select all and delete, cut, paste over, drop, Discard, a draft coming back and Send emptying the box are a step each, and so is a box emptied after a failed send.
- A box with a draft keeps its last 50 steps when you switch chats or tabs, and with Save drafts on, through a restart (the steps are saved with the draft). Undo works right after a draft comes back or is discarded.

### Defaults used
- Setup's own task box and the skill editor aren't given drafts: setup already keeps its progress, and the skill editor has Save.
- Plain boxes (setup's answer, a routine, a question's answer) clear their draft when submitted; only the message boxes wait for Still's answer.
- Discard deletes the stored draft at once; undo in the same session still brings the text back.
- Two windows open at once don't see each other's draft changes; each loads the drafts when it opens.
- Undo in boxes with no draft (Settings search and the like) lasts while the box is open.
